# Phase 12D11 · RapidOCR rollback startup gate

RB-1 is a pre-existing v1.2.0 rollback requirement. The baseline stays at `f2fdf2714a7c0b5b196132f71cfc091928befc06`. A fresh baseline container installs Docling and RapidOCR from its uv cache. The recognizer weights survive on the data volume, while RapidOCR resolves the dictionary in the installed package. The dictionary has to be restored after the package is installed on each fresh container.

The Windows 12F1 lab validated RB-G1 through RB-G10. The final RB-G10 rerun preserved 22/22 tables including `user`, with equal data and schema digests and the same DB container ID (`restarts=0`). The recorded order was baseline entrypoint installing RapidOCR, helper restoring the dictionary, supervisord starting, then the worker spawning. Offline RapidOCR returned 10/10 tokens, using `RapidOcrModel` with torch. RB-G11 Ubuntu VM reboot is pending. Record the target restart policy before that rehearsal.

## Package and startup

- A package based on the official v1.2.0 commit requires SSH manifest signing. Its file inventory includes the pinned 74,947-byte dictionary, verified Local restore helper and asset manifest, Apache-2.0 license, integration scripts and runtime gate. Both the signer and the full file inventory are checked. The release signing key stays outside the package. [RapidOCR v3.9.2](https://github.com/RapidAI/RapidOCR/tree/v3.9.2)
- `rb1_setup.py` verifies the signed tree, running baseline image, exact deployment tag and configured persistent volume. It probes the live v1.2.0 runtime in check-only mode, then tests the same image's offline initialization in a disposable network-disabled container. It uses a read-only data mount and scratch cache inside that container. `A-valid` covers an existing valid dictionary. `B-recoverable` covers a missing dictionary with verified prerequisites. Every other case refuses the update.
- `--stage` is a separate explicit action. It puts the signed assets and an application-only Compose override in a persistent host directory. The selector uses the full baseline image ID and deployment tag to provide the override in normal, maintenance and boot guard paths. The startup wrapper checks the pinned original entrypoint and offline configuration, invokes the baseline entrypoint, verifies the runtime and model hashes, installs the dictionary safely, then execs supervisord. Helper errors stop startup. No live production adapter was edited.

The verified combination is RapidOCR 3.9.2, CPU torch 2.14.0+cpu, Docling 2.129.0, the pinned PP-OCRv6 recognition weights and shipped YAML, and persistent RapidOCR settings. Other backends and configurations refuse preflight until separately verified. The upstream dictionary is pinned to the ModelScope `v3.9.2` artifact documented in the asset manifest. Its SHA-256 and size matched both reference copies in the Local handover. The pinned Apache license was taken from that release. [RapidOCR license at v3.9.2](https://github.com/RapidAI/RapidOCR/blob/v3.9.2/LICENSE)

## Integration evidence and pending checks

The regression tests exercise a signed package with real SSH signatures and a fake Docker image, checksum and missing-asset refusal, both preflight success cases and failure, the persistent Compose selector, and shell startup order repeatedly. The Local restore helper is unchanged. The exact official image, Compose adapter, network-disabled cache rehearsal and Ubuntu VM reboot are Windows/Local acceptance items. See D11-W09.

The unchanged F0 seed and mutation matrix exercised 12 embeddings and **8/8** positive controls on isolated embedded SurrealDB. N0 passed when a real `LIVE SELECT * FROM command` subscription changed `INFO FOR TABLE command`. The schema and business fingerprint stayed identical. The earlier Windows N0 rehearsal used a worker restart. Replaying the worker restart on the official packaged candidate is part of D11-W09. The data probe includes the five primary content tables plus `reference`, `artifact` and `user`. It omits transient command/LIVE subscription metadata and `recently_viewed` activity. RB-G10's separate 22-table preservation verdict covers the wider Local database snapshot.
